## What the REST spec does NOT cover (and what it does, contrary to common belief) — checked 2026-10-05

### R2 objects
- The spec DOES contain object-level endpoints (tag `R2 Object`, 5 ops): `GET /accounts/{account_id}/r2/buckets/{bucket_name}/objects` (list; params per_page, prefix, delimiter, cursor, start_after), `GET|PUT|DELETE .../objects/{object_key}`, `DELETE .../objects` (bulk). PUT is `application/octet-stream`, max 300 MB per the description; GET returns the body as octet-stream. Each description says "For most workloads, we recommend using R2's S3-compatible API ... or a Worker with an R2 binding instead."
- NOT in the spec: multipart uploads, presigned URLs, copy, object metadata update, lifecycle-driven listing of versions. Those need the S3 API (`https://<account_id>.r2.cloudflarestorage.com`) with separate R2 S3 credentials (created at `POST /accounts/{account_id}/r2/temp-access-credentials` for temporary ones, or in the dashboard for permanent ones; permanent S3 keys are not creatable via this spec).
- Bucket-level config IS covered: CORS, custom domains, managed (r2.dev) domain, lifecycle, lock, sippy, metrics, event notifications, super slurper jobs, data catalog (Iceberg).

### D1
- Covered: list/create/get/update/delete, `POST .../query` and `POST .../raw`, `POST .../export` (async; returns a download URL, poll with the same call), `POST .../import`.
- Time travel IS covered: `GET .../time_travel/bookmark` and `POST .../time_travel/restore?bookmark=|timestamp=`.
- NOT covered: no schema/table-listing endpoint (use `query` with `sqlite_master`), no read-replication toggle beyond the PATCH body, no per-query metrics (GraphQL `d1QueriesAdaptiveGroups`).

### Queues
- Covered (28 ops): queue CRUD, consumers CRUD, purge (`POST/GET .../purge`), and the HTTP pull-consumer message endpoints: `messages/pull`, `messages/ack`, `messages/extend` (lease), `messages/peek` (no lease), `messages/preview` and `messages/preview/ack`, `messages` and `messages/batch` (push), `messages/purge`.
- Caveat: pull/ack only work on a queue that has an HTTP pull consumer configured; peek/preview are the "inspect without consuming" path a TUI would use.
- NOT covered: dead-letter-queue browsing beyond treating the DLQ as another queue; per-message redelivery counts in list form.

### Workers tail / logs
- `POST /accounts/{account_id}/workers/scripts/{script_name}/tails` returns `{id, url, expires_at}` — `url` is a WebSocket URL (wss://tail.developers.workers.dev/...) that the client must connect to; the REST call only creates the tail session. `GET .../tails` lists, `DELETE .../tails/{id}` ends it. Pages has the same shape under `.../deployments/{deployment_id}/tails`.
- Workers Logs (observability): `POST /accounts/{account_id}/workers/observability/telemetry/query` (historical query), `telemetry/keys`, `telemetry/values`, `telemetry/live-tail` (returns `wsUrl`) + `live-tail/heartbeat`, plus saved `queries`, `issues`, `destinations`, `metricsexport`, `usage`. So historical logs ARE queryable over REST (POST JSON), but streaming is WebSocket-only in both tail flavours.
- There is no REST endpoint that returns a plain array of recent log lines without first enabling Workers Logs (`observability.enabled` in script settings).

### Durable Objects
- Covered: `GET /accounts/{account_id}/workers/durable_objects/namespaces` (list namespaces), `GET .../namespaces/{id}/objects` (list object IDs — paginated with cursor; this is the "can DO objects be listed?" answer: yes, IDs only, with `hasStoredData` flag), and `POST .../namespaces/{id}/query/v2` ("Executes one or more SQL queries against a Durable Object"; body is query-by-id or query-by-name) — i.e. SQLite-backed DO storage CAN be inspected over REST.
- NOT covered: KV-backed (legacy) DO storage inspection, alarms, WebSocket connection counts, deleting a single object's storage, DO class migrations (those go through the script upload metadata).

### Workers (scripts)
- Covered: scripts CRUD (multipart upload), `content` get/put, `settings`/`script-settings`, `secrets` (+ `secrets-bulk`), `schedules` (cron triggers), `subdomain` (workers.dev + previews), `domains` (custom domains), `usage-model`, `versions` (+ create), `deployments` (gradual rollouts), `assets-upload-session`, `scripts-search`, account `subdomain`, `account-settings`, placement regions, zone `routes`, and the newer `/workers/workers/{worker_id}` resource model (previews, versions/latest).
- Bindings are set only via the script/version upload metadata — there is no standalone "bindings" endpoint.
- NOT covered: the dashboard's in-browser editor/Quick Edit (uses the same upload API), Workers Builds triggers beyond `builds/*` endpoints (which require a user token, not an account token per docs).

### Other notable absences
- GraphQL analytics (all charts in the dashboard) are not in this spec; `POST https://api.cloudflare.com/client/v4/graphql` is a separate schema (see auth notes).
- Logpull (`/zones/{zone_id}/logs/received`) and Logpush are present, but Instant Logs is a WebSocket session created via `instant_logs` jobs.
- Account-owned API tokens cannot be used for: Page Rules, Registrar, Turnstile, Intel Data Platform, Super Bot Fight Mode, Zero Trust Client Platform (docs compatibility matrix), and `/memberships` / `/user` (user-scoped; account tokens get error code 9106 there).
- Zaraz has 10 endpoints under `/zones/{zone_id}/settings/zaraz/*` (config, default, export, history, publish, workflow).
- Workers AI: `POST /accounts/{account_id}/ai/run/{model_name}` plus models/authors/tasks/finetunes; AI Gateway is fully CRUD-able (gateways, logs, datasets, evaluations, provider configs, dynamic routes, custom domains).
