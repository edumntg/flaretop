# Cloudflare COMPUTE products over the HTTP API — what a Rust TUI can and cannot do

Researched 2026-10-05. Sources: the public OpenAPI schema (`cloudflare/api-schemas` `openapi.json`, 2,287 paths, pulled today), the API reference at https://developers.cloudflare.com/api/, product docs, the `cloudflare/workers-sdk` wrangler source (`packages/wrangler/src/...`, `main` branch), and live **GET** probes against a real account with a read-only token (responses redacted; ids replaced by `<id32>`/`<uuid>`).

Conventions used below
- Base URL: `https://api.cloudflare.com/client/v4`. Auth: `Authorization: Bearer <token>`. Every JSON response is the envelope `{success, errors[], messages[], result, result_info?}`.
- Pagination is NOT uniform. Four families exist and a TUI must handle all four: (a) `page`/`per_page` + `result_info{page,per_page,count,total_count,total_pages?}`; (b) `page`/`per_page` but **no `result_info`** (Workers script list, tails list, secrets); (c) `cursor`-based (`result_info.cursor`, Workflows instances, audit logs v2); (d) `page_token` (Containers).
- "Live probe" lines show what the real API returned to a GET today. When a probe returned 403 with error code 10000 "Authentication error", that is a missing token permission, not a missing endpoint; the permission needed is noted.

Token permissions this read-only token had (from `GET /zones` `permissions[]`): `#worker:read/edit`, `#d1:edit`, `#r2_bucket*`, `#analytics:read`, `#zone:read`, `#auditlogs:read`, `#member:read`, `#access:*`, `#dns_records:*`, `#organization:*`. It did NOT have Pages, Workers AI, AI Gateway, Containers, Logpush, Images, Stream, Email Routing, Browser Rendering, Billing, Workers Observability, Workers Routes (zone), Workers for Platforms. A TUI should ship a token-verification screen (`GET /user/tokens/verify` → `{id,status}`) and a permission checklist.

## 1. Workers scripts — verdict: FULL

Docs: https://developers.cloudflare.com/api/resources/workers/subresources/scripts/ and https://developers.cloudflare.com/workers/configuration/multipart-upload-metadata/

### 1.1 List scripts
`GET /accounts/{account_id}/workers/scripts` — query `tags` (`tag:yes,other:no`). Live probe (HTTP 200): returns ALL scripts (14) in one page; `per_page` is ignored and `result_info` is absent. Real fields per item:

```
id (script name), tag (32-hex script id), tags[], created_on, modified_on, etag,
deployment_id, usage_model ("standard"|"bundled"|"unbound"), handlers[] (e.g. ["fetch","scheduled"]),
last_deployed_from ("wrangler"|"dash"|"api"), compatibility_date, compatibility_flags[],
has_assets, has_modules, logpush, tail_consumers (null|[{service,environment?,namespace?}]),
routes (null|[]), placement (object, may be absent),
observability {enabled, head_sampling_rate, redact_query_string,
               logs {enabled, head_sampling_rate, persist, invocation_logs},
               traces {enabled, persist, head_sampling_rate}}
```
Schema also lists `cache_options`, `exports` (entrypoints and DO declarations), `placement{mode,hint?,region?,status}`.

Paginated and searchable alternatives (live-probed 200):
- `GET /accounts/{id}/workers/scripts-search?name=&id=&order_by=created_on|modified_on|name&page=&per_page=` → `[{id (tag), script_name, created_on, modified_on}]` (name substring match).
- `GET /accounts/{id}/workers/workers?page=&per_page=&order_by=deployed_on|updated_on|created_on|name&order=asc|desc` — the newer "Workers" resource (id = tag). Returns `result_info{page,per_page,count,total_count}` and per item: `id, name, tags[], observability{...}, logpush, created_on, updated_on, deployed_on, subdomain{enabled, previews_enabled, url}, tail_consumers[], previews_base_config, references{workers[], domains[], dispatch_namespace_outbounds[], durable_objects[{worker_id,worker_name,namespace_id,namespace_name}], queues[]}`. The `references` block is exactly the "what binds to this Worker" data the dashboard shows and is not available anywhere else. Sibling endpoints: `POST/GET/PUT/PATCH/DELETE /workers/workers/{worker_id}`, `.../versions` (`GET`, `POST ?deploy=true` JSON body with `main_module`, `modules[]`, `bindings[]`, `compatibility_date`, `limits`, `migrations`, `containers[]`, `assets{config,jwt}`, `package_dependencies[]`), `.../versions/latest` (`GET/PATCH`), `.../previews` (`GET/POST`, `?ignore_defaults&ignore_base_config`), `.../previews/{preview_id}/deployments`. This JSON-only version API is the one `wrangler versions upload`'s newer code path and the dashboard use; it avoids multipart.

### 1.2 Get a script's content (download the bundle)
- `GET /accounts/{id}/workers/scripts/{name}/content/v2` and `GET /accounts/{id}/workers/scripts/{name}` both return **`Content-Type: multipart/form-data; boundary=...`** (live probe: 200, 2.3 MB for a Worker with wasm). Each part: `Content-Disposition: form-data; name="<module path>"; filename="<module path>"` and `Content-Type: application/javascript+module | application/wasm | text/plain | application/octet-stream | application/source-map`. Headers carry `etag` and `last-modified`. A classic service-worker-syntax script comes back as a single `application/javascript` body instead. Rust: parse with `multer`/`multipart` using the boundary from the header; module names are the keys. No `metadata` part is returned — fetch settings separately.
- Per-version content: `GET /accounts/{id}/workers/scripts/{name}/versions/{version_id}` returns JSON with `resources.script{etag,handlers,last_deployed_from}`, `resources.script_runtime{compatibility_date,compatibility_flags,usage_model,limits?,assets{headers{version,rules},raw_headers,serve_directly,raw_run_worker_first}}`, `resources.bindings[]` and `metadata{created_on,source,author_id,author_email,has_preview}` (live probe). Version content (modules) is not downloadable per version through the public API.

### 1.3 Settings (bindings, compat, limits, logpush, observability, tail consumers)
- `GET /accounts/{id}/workers/scripts/{name}/settings` — live probe 200: `placement{}, compatibility_date, compatibility_flags[], usage_model, tags[], tail_consumers[], logpush, observability{...}, annotations{"workers/triggered_by"}, bindings[]`. Binding items are typed by `type`: `plain_text{name,text}`, `secret_text{name}` (value NOT returned), `d1{name,id,database_id}`, `r2_bucket{name,bucket_name}`, `kv_namespace{name,namespace_id}`, `assets{name}`, `durable_object_namespace{name,class_name,script_name?}`, `service{name,service,environment?,entrypoint?}`, `queue{name,queue_name}`, `ai`, `analytics_engine{dataset}`, `browser`, `hyperdrive{id}`, `vectorize{index_name}`, `mtls_certificate{certificate_id}`, `version_metadata`, `dispatch_namespace{namespace,outbound?}`, `secrets_store_secret{store_id,secret_name}`, `workflow{workflow_name,class_name,script_name?}`, `pipelines`, `images`, `ratelimit{namespace_id,simple{limit,period}}`, `wasm_module`, `text_blob`, `data_blob`, `json`, `inherit`, `secret_key{algorithm,format,usages}`, `send_email{destination_address?,allowed_destination_addresses?}`, `worker_loader`, `media`, `vpc_service`. The full enum in the schema has 36 types.
- `PATCH /accounts/{id}/workers/scripts/{name}/settings` — **multipart/form-data** with one part named `settings` containing JSON of `workers_script-and-version-settings-item`: `bindings[]`, `compatibility_date`, `compatibility_flags[]`, `limits{cpu_ms, subrequests}`, `logpush`, `migrations` (DO: `{new_tag, old_tag, new_classes[], new_sqlite_classes[], deleted_classes[], renamed_classes[], transferred_classes[]}` or `{steps[]}`), `observability{enabled, head_sampling_rate, redact_query_string, logs{...}, traces{...}, issues?}`, `placement{mode:"smart"}`, `tags[]`, `tail_consumers[{service,environment?,namespace?}]`, `usage_model`, `annotations{"workers/message","workers/tag"}`, `cache_options{enabled, cross_version_cache}`, `exports`, `exports_reconciliation`. `wrangler deploy` calls this right after deploying (audit action `patch_settings`). Note: PATCH replaces `bindings` as a whole — to keep secrets you must include `{"type":"secret_text","name":...}` entries without `text` (or use the `inherit` binding type).
- Lighter, JSON-only variant: `GET/PATCH /accounts/{id}/workers/scripts/{name}/script-settings` — body `{logpush, observability, tags, tail_consumers}` only (live probe 200).
- Usage model: `GET/PUT /accounts/{id}/workers/scripts/{name}/usage-model` body `{usage_model:"standard"|"bundled"|"unbound", user_limits{cpu_ms}}` (live GET returned 415 unless `Content-Type: application/json` is sent even on GET — send it).

### 1.4 Upload a script (multipart)
`PUT /accounts/{id}/workers/scripts/{name}` (query `bindings_inherit=strict` optional), `Content-Type: multipart/form-data`:
- part `metadata` (`application/json`): `main_module` (ES modules) **or** `body_part` (service-worker syntax), `bindings[]`, `compatibility_date`, `compatibility_flags[]`, `usage_model`, `placement`, `tail_consumers[]`, `logpush`, `observability`, `limits`, `migrations`, `tags[]`, `annotations{"workers/message","workers/tag"}`, `keep_bindings[]` (binding types to carry over, e.g. `["secret_text"]` — this is how you preserve secrets on upload), `keep_assets` (bool), `assets{jwt, config{html_handling, not_found_handling, run_worker_first, _headers, _redirects, serve_directly}}`, `cache_options`, `exports`, `containers[]`.
- one part per module, part name = module path, with content-type `application/javascript+module`, `application/wasm`, `text/plain`, `application/octet-stream`, `application/source-map`, or `text/x-python` (Python Workers). Returns the script object with `startup_time_ms`.
- Alternatives: `PUT /accounts/{id}/workers/scripts/{name}/content` (content only, keeps settings; needs `metadata{main_module|body_part}` and `CF-WORKER-BODY-PART`/`CF-WORKER-MAIN-MODULE-PART` headers) and the legacy environments path `PUT /accounts/{id}/workers/services/{service}/environments/{env}/content` (+ `.../settings`).
- Static assets flow (public, used by wrangler; docs https://developers.cloudflare.com/workers/static-assets/direct-upload/): `POST /accounts/{id}/workers/scripts/{name}/assets-upload-session` body `{manifest: {"/path": {hash, size}}}` → `{jwt, buckets: [[hash,...],...]}`; for each bucket `POST /accounts/{id}/workers/assets/upload?base64=true` multipart with fields named by hash, base64 content, `Authorization: Bearer <session jwt>` → last response carries a completion `jwt`; then upload the script with `metadata.assets.jwt`. Hash = SHA-256 of (base64(content) + file extension) hex, truncated to 32 chars. Empty `buckets` means the jwt is already a completion token. Live probe: GET on the session endpoint returned 405 as expected (POST only).
- `DELETE /accounts/{id}/workers/scripts/{name}?force=true` (force deletes even with DO namespaces/consumers attached).

What `wrangler deploy` actually does today (confirmed from this account's audit log for a deploy on 2026-09-21): `script_update` = `POST .../versions` (multipart, same metadata as above) → `script_deploy` = `POST .../deployments` → `patch_settings` = `PATCH .../settings` → `script_on_subdomain` = `POST .../subdomain` → `script_schedules` = `PUT .../schedules` → queue `update_consumer_settings`. All of these are public endpoints; wrangler has no private path here.

### 1.5 Schedules (cron triggers)
`GET /accounts/{id}/workers/scripts/{name}/schedules` → `{schedules:[{cron, created_on, modified_on}]}` (live 200). `PUT` same path with body `[{cron:"17 3 * * *"}, ...]` replaces the whole set.

### 1.6 Secrets
- `GET /accounts/{id}/workers/scripts/{name}/secrets` → `[{name, type:"secret_text"|"secret_key"}]` (live 200). **Values are never readable** by any endpoint, including `/settings` and `/content` — the TUI can only list names, set, and delete.
- `PUT /accounts/{id}/workers/scripts/{name}/secrets` body `{name, text, type:"secret_text"}` (or `{name, type:"secret_key", algorithm, format:"raw"|"pkcs8"|"spki"|"jwk", usages[], key_base64|key_jwk}`). Each call creates a new version (annotation `workers/triggered_by: "secret"`).
- `PATCH /accounts/{id}/workers/scripts/{name}/secrets-bulk` — JSON Merge Patch: `{secrets: {NAME: {type,text} | null}, version_tags?}` (null deletes). Prefer this for multiple secrets (one new version). wrangler `secret bulk` uses it.
- `GET/DELETE /accounts/{id}/workers/scripts/{name}/secrets/{secret_name}`.
- wrangler's `versions secret put/bulk/delete` work differently: they read `GET .../versions`, then create a new version via `POST .../versions` carrying the full binding list with secrets, so a later deployment can pick it up; secrets then are not live until deployed.

### 1.7 Environment variables
Plain-text vars are `plain_text` bindings (`{type:"plain_text", name, text}`) and `json` bindings; edit them through `PATCH .../settings` (full `bindings` array) or by uploading a new version. There is no per-variable endpoint. The dashboard "Variables and Secrets" page is exactly this.

### 1.8 workers.dev subdomain
- Account: `GET /accounts/{id}/workers/subdomain` → `{subdomain}` (live 200); `PUT` body `{subdomain}` creates/renames (rename is allowed once chosen? the API returns an error if taken); `DELETE` removes it.
- Per script: `GET /accounts/{id}/workers/scripts/{name}/subdomain` → `{enabled, previews_enabled}` (live 200); `POST` body `{enabled: bool, previews_enabled?: bool}`; `DELETE` disables.
- Account settings: `GET/PUT /accounts/{id}/workers/account-settings` body `{default_usage_model, green_compute}` (live 200 `{default_usage_model:"standard", green_compute:false}`).

### 1.9 Custom domains and routes
- Custom domains (account-level): `GET /accounts/{id}/workers/domains` (live 200, `result_info` present; filters `zone_name, zone_id, hostname, service, environment`) → `[{id, zone_id, zone_name, hostname, service, environment, cert_id, previews_enabled?, enabled?}]`; `PUT /accounts/{id}/workers/domains` body `{hostname, service, zone_id, environment:"production"}` attaches (creates the DNS record and cert); `GET/DELETE /accounts/{id}/workers/domains/{domain_id}`.
- Routes (zone-level): `GET/POST /zones/{zone_id}/workers/routes` body `{pattern, script}`; `GET/PUT/DELETE /zones/{zone_id}/workers/routes/{route_id}`. Live probe: 403 "No access to the specified resource" — needs zone-scoped **Workers Routes: Read/Edit** on the zone. A TUI must list zones (`GET /zones?per_page=50&page=N`, 200 today) and then iterate per zone; there is no account-wide route listing (the `routes` field in the script list came back `null` in practice).

### 1.10 Versions and deployments (gradual rollouts, rollback)
Docs: https://developers.cloudflare.com/workers/configuration/versions-and-deployments/ and https://developers.cloudflare.com/workers/configuration/versions-and-deployments/gradual-deployments/
- `GET /accounts/{id}/workers/scripts/{name}/versions?deployable=true&page=&per_page=` → `{items:[{id, number, metadata{created_on, source, author_id, author_email, has_preview}, annotations{"workers/triggered_by","workers/message","workers/tag"}}]}` (live 200; 50 versions kept; the shape is `result.items`, not a bare array, and there is no `result_info`). `triggered_by` values seen: `version_upload`, `deployment`, `upload`, `secret`, `rollback`, `promotion`.
- `GET .../versions/{version_id}` — full version (see 1.2).
- `POST /accounts/{id}/workers/scripts/{name}/versions` (multipart; metadata keys `main_module, bindings, compatibility_date, compatibility_flags, usage_model, keep_bindings, annotations, cache_options, exports, package_dependencies`; query `bindings_inherit=strict`) → version with `startup_time_ms`. Uploads without deploying (preview URL available when `has_preview`).
- `GET /accounts/{id}/workers/scripts/{name}/deployments?since=&until=&page=&per_page=` → `{deployments:[{id, source, strategy:"percentage", author_email, annotations{"workers/message","workers/triggered_by"}, versions:[{version_id, percentage}], created_on}]}` (live 200, newest first).
- `POST /accounts/{id}/workers/scripts/{name}/deployments?force=true` body `{strategy:"percentage", versions:[{version_id, percentage}], annotations:{"workers/message":"..."}}`. Percentages must sum to 100; this is gradual rollout. **Rollback** has no dedicated endpoint: it is a new deployment with the older version at `100` (wrangler `rollback` does exactly this and sets `workers/message`; the audit log shows it as `script_deploy`). `force` skips the "version has DO migrations / is not deployable" guard. `GET/DELETE .../deployments/{deployment_id}`.
- Version affinity/preview: previews are `https://<version-prefix>-<name>.<subdomain>.workers.dev` and need `previews_enabled` on the script subdomain.

### 1.11 Tail consumers, placement, limits, tags
All are fields of `/settings` (1.3). `GET /accounts/{id}/workers/placement/regions` → `{providers:[{id:"aws"|"gcp"|..., regions:[{id}]}]}` (live 200) for targeted placement. Tags: `tags[]` in settings; dispatch-namespace scripts additionally get `GET/PUT .../tags` and `PUT/PATCH/DELETE .../tags/{tag}`.

### 1.12 Durable Objects (adjacent)
`GET /accounts/{id}/workers/durable_objects/namespaces` → `[{id, name, script, class, use_sqlite}]` (live 200, `result_info` present); `GET .../namespaces/{id}/objects?limit=&cursor=` (list object ids, `hasStoredData`); `POST .../namespaces/{id}/query/v2` (SQL against SQLite-backed DOs — the dashboard's DO SQL explorer). No create/delete: namespaces exist only via `migrations` in a version upload.

### 1.13 Workers for Platforms (brief)
`GET/POST /accounts/{id}/workers/dispatch/namespaces` body `{name}`; `GET/PUT/PATCH/DELETE .../{ns}`; `GET/DELETE .../{ns}/scripts`; per user Worker `GET/PUT/DELETE .../{ns}/scripts/{name}` (PUT is the same multipart as 1.4), plus `/content`, `/settings`, `/secrets`, `/secrets-bulk`, `/bindings`, `/tags`, `/assets-upload-session`. Live probe: 403 code 10121 "You do not have access to dispatch namespaces" — a paid add-on, not a permission.

### 1.14 Dashboard-only things for Workers
- Workers Builds (Git integration): config is readable/editable via `GET/PATCH/DELETE /accounts/{id}/builds/workers/{script_tag}` (result `{git_repository, previews_enabled, previews_base_config, production_settings, script_tag}`), `GET .../builds`, `GET .../triggers`, deploy hooks (`GET/POST /builds/workers/{name}/deploy_hooks`, public trigger `POST /workers/builds/deploy_hooks/{uuid}`), previews. Live probe: 404 code 12040 "No build configuration" for a wrangler-deployed script (expected). **Installing the GitHub/GitLab App is an OAuth dance only the dashboard can do**; everything after that is API.
- Quick Edit / Playground: the editor itself and the "edge preview" session it uses are internal; `wrangler dev --remote` uses `/accounts/{id}/workers/scripts/{name}/edge-preview` + `/accounts/{id}/workers/subdomain/edge-preview` (undocumented, returns an `inspector_websocket` and preview token). A TUI can upload a version and hit its preview URL instead.
- Templates / "Create from template" gallery, the Workers "Observability" charts (GraphQL + telemetry query, see §2), and account-level Compliance/Region settings are dashboard UI over public data.
- Everything else on the Worker page (settings, triggers, domains, variables, versions, deployments, tail consumers, placement, tags, deleting) maps 1:1 to the endpoints above.

## 2. Workers logs — verdict: FULL (tail), FULL (stored logs query), with permission caveats

### 2.1 `wrangler tail` — the Tail API (implementable in Rust)
Docs: https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/tails/ and wrangler `src/tail/createTail.ts`, `src/tail/filters.ts`, `src/tail/index.ts`.

1. `POST /accounts/{id}/workers/scripts/{name}/tails` with JSON body `{"filters":[...]}` (may be `{"filters":[]}`) → `result {id, url, expires_at}`. `url` is `wss://tail.developers.workers.dev/<id>`; `expires_at` is ~a few hours out. `GET .../tails` lists active tails (live probe 200, `[]`); `DELETE .../tails/{id}` ends it (do this on exit; wrangler does). Needs **Workers Scripts: Edit** (the audit log records `tail_logs_start`/`tail_logs_end`). Pages Functions have the same shape at `POST /accounts/{id}/pages/projects/{project}/deployments/{deployment_id}/tails`.
2. Open the WebSocket to `url` with the sub-protocol **`trace-v1`** (`Sec-WebSocket-Protocol: trace-v1`; wrangler also sends a `User-Agent`). Without `trace-v1` the server refuses.
3. On open, send one text frame: `{"debug": false}` (wrangler sends `JSON.stringify({debug})`; filters go in the POST body, not over the socket — current wrangler code sends only the debug flag).
4. Keepalive: wrangler sends a WebSocket **ping frame** with payload `"wrangler tail ping"` every **10 s** and expects a pong carrying the same bytes; if no pong within the interval it treats the connection as dead and reconnects (backoff 1,2,4,8,16 s, five attempts, re-creating the tail via POST). The backend does **not** close the socket at `expires_at` — delivery just stops, so the client must refresh (re-POST) before expiry. Normal close code 1000 means the server ended the session.
5. Filters (POST body `filters[]`, union of):
   - `{"sampling_rate": 0.25}`
   - `{"outcome": ["ok","canceled","exception","exceededCpu","exceededMemory","unknown"]}` (CLI `--status ok|error|canceled`; `error` expands to `exception,exceededCpu,exceededMemory,unknown`)
   - `{"method": ["GET","POST"]}`
   - `{"header": {"key": "X-Foo", "query": "value"}}` (query optional)
   - `{"client_ip": ["1.2.3.4"]}` (CLI `self` resolves to the caller's IP)
   - `{"query": "substring"}` (full-text match on the event)
   - `{"scriptVersion": "<version id>"}`
6. Message format (one JSON text frame per event, `TailEventMessage`):
   ```
   { outcome: "ok"|"canceled"|"exception"|"exceededCpu"|"exceededMemory"|"unknown",
     scriptName?, entrypoint?, scriptVersion?: {id, tag?, message?},
     eventTimestamp: <ms>,
     logs: [{message: any[], level: "debug"|"info"|"log"|"warn"|"error", timestamp}],
     exceptions: [{name, message, timestamp, stack?}],
     diagnosticsChannelEvents?: [{timestamp, channel, message}],
     event: RequestEvent | ScheduledEvent | AlarmEvent | EmailEvent | TailEvent | QueueEvent | RpcEvent | TailInfo | null }
   ```
   `RequestEvent = {request: {url, method, headers{...}, cf{colo, country, asn, tlsVersion, tlsCipher, clientTcpRtt?, httpProtocol, ...}}, response?: {status}}`; `ScheduledEvent = {cron, scheduledTime}`; `AlarmEvent = {scheduledTime}`; `EmailEvent = {mailFrom, rcptTo, rawSize}`; `QueueEvent = {queue, batchSize}`; `RpcEvent = {rpcMethod}`; `TailEvent = {consumedEvents:[{scriptName}]}`; `TailInfo = {message, type:"overload"|"overload-stop"}` — the backend sends `overload` when the Worker is too busy and `overload-stop` when it resumes; a TUI should surface those.
7. Limits: one Worker can have a small number of concurrent tails (10 per account/script; the API returns code 10079 beyond). High-volume Workers get sampled (`TailInfo` overload). `wrangler tail --format json` prints these frames verbatim, so a Rust implementation can be tested against wrangler output.

### 2.2 Workers Logs / Observability (persistent logs) — there IS a public query API
Docs: https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/ ; product: https://developers.cloudflare.com/workers/observability/logs/workers-logs/ and https://developers.cloudflare.com/workers/observability/query-builder/
- Enablement per script: `observability{enabled, head_sampling_rate, logs{enabled, persist, invocation_logs, head_sampling_rate}, traces{...}}` via `PATCH .../settings` or `/script-settings`. Retention 3 days (Free) / 7 days (Paid); 200k logs/day free, 20M/month included paid, $0.60/M after; 256 KB per log; 5B/day account cap. Pricing moves to "Cloudflare Observability" pricing on 2026-12-01.
- Required permission: **Workers Observability (Read/Edit)** — this token lacked it, so all probes below returned 403 code 10000. (A GET to `/accounts/{id}/workers/scripts/{name}/observability/telemetry/query` returned 200 multipart — that is only the `GET /workers/scripts/{name}` download route swallowing the suffix; ignore it.)
- `POST /accounts/{id}/workers/observability/telemetry/query` body:
  ```
  { queryId: "<any string, e.g. uuid>",
    timeframe: {from: <unix ms>, to: <unix ms>},
    view: "events"|"invocations"|"calculations"|"traces"|"requests"|"agents" (default calculations),
    limit: <=2000 (default 50), offset: "<cursor from previous page>", offsetBy, offsetDirection,
    dry, chart, chartType: "timeseries_and_aggregate"|"timeseries"|"aggregate"|"distribution", granularity, compare, ignoreSeries,
    parameters: {
      datasets: ["cloudflare-workers"]   // omit/empty = all datasets
      filters: [{key:"$metadata.service", operation:"eq", value:"bakepdf", type:"string"}, ... ]  // nested groups: {kind:"group", filterCombination:"and"|"or", filters:[...]}
      filterCombination: "and"|"or",
      calculations: [{operator:"count"} | {operator:"avg"|"sum"|"min"|"max"|"median"|"p50".."p999"|"stddev"|"variance"|"uniq", key:"$workers.cpuTimeMs", keyType:"number", alias?}],
      groupBys: [{type:"string", value:"$workers.outcome"}],
      havings: [{key, operation, value}],
      orderBy: {value, order:"asc"|"desc"},
      needle: {value:"text", isRegex?, matchCase?},  // full-text search
      limit } }
  ```
  Filter operations: `includes, not_includes, starts_with, ends_with, regex, exists, is_null, in, not_in, eq, neq, gt, gte, lt, lte` (also `=,!=,>,>=,<,<=` and uppercase aliases). Response `result{run{...}, statistics{...}, events{count, events[], fields[{key,type}], series[]}, invocations{<requestId>: [events]}, calculations[], traces[], compare[], distribution}`. Each event: `{dataset, timestamp(ms), source: string|object (raw console payload), $metadata{service, type:"cf-worker-event"|"cf-worker-log", level, message, trigger ("GET /path"), requestId, rayId, error, account, origin, region, statusCode, url, traceId, spanId, duration, coldStart, cost,...}, $workers{scriptName, scriptVersion, outcome, eventType, executionModel, entrypoint, requestId, cpuTimeMs, wallTimeMs, event{request{url,method,path,cf{country}...}, response{status}}, durableObjectId, dispatchNamespace, diagnosticsChannelEvents, truncated}, $containers?}`. Invocation (one per request) events are `$metadata.type == "cf-worker-event"`.

Practical notes for the Rust client
- Multipart is needed in three places only: script/version upload (`PUT /workers/scripts/{name}`, `POST .../versions`), `PATCH .../settings` (single `settings` part), and Pages deployment create; everything else is JSON. Script download is multipart on the way back. Use `reqwest` multipart with explicit `Content-Type` per part; the JSON `/workers/workers/{id}/versions` API avoids multipart entirely if you prefer.
- Expect three list shapes for Workers: bare array without `result_info` (`/workers/scripts`, `/secrets`, `/tails`), `result.items[]` (`/versions`), `result.deployments[]` / `result.schedules[]` wrappers, and `result_info` only on `/workers/domains`, `/workers/workers`, `/workflows*`, `/durable_objects/namespaces`, `/zones`.
- The API sets `__cflb`/`__cf_bm` cookies on `api.cloudflare.com`; ignore them. Responses on download endpoints are not gzip-encoded unless you ask; do not double-decompress.
- Timestamps: Workers REST uses RFC 3339 strings; telemetry `timeframe` and `usage` use **unix milliseconds**; Workflows retention values are **milliseconds**; audit logs `since/before` are RFC 3339.
